# Backend patterns (tender-chat-v1)

Status: **planned, not built yet.** `db/schema.ts` is empty and none of the classes below exist. Patterns follow the approved Plan 01 (`.claude/plans/01-auth.md`, sections Classes and Build steps). Once code lands, check each example against the real file and cite `path:line` here instead.

## Layout and naming

Plan 01 moves code into `src/` (`@/*` → `./src/*`), one folder per area:

| Folder | Holds |
| --- | --- |
| `src/app/api/**/route.ts` | HTTP handlers only: get the controller from the container, call one method |
| `src/backend/lib/` | **plain functions, no classes**: `config.ts` (env checked once with zod), `password.ts`, `tokens.ts` (jose), `cookies.ts`, `request.ts` (`readJson`, `readDevice`), `rate-limit.ts` |
| `src/backend/database/` | `Database` class (pg Pool max 3 + Drizzle, one instance across hot reloads), schema, migrations |
| `src/backend/errors/` | `AppError` + one file per subclass, `toErrorResponse()` |
| `src/backend/<area>/` | `<Area>Repository`, `<Area>Service`, `<Area>Controller` classes (`users/`, `auth/`, `oauth/`) |
| `src/backend/container.ts` | The only place that calls `new` on backend classes |
| `src/contracts/` | zod schemas shared by forms and routes (`auth.contracts.ts`) |

## How many classes (owner rule: minimal OOP)

- Classes only for `Database`, repositories, services and controllers. One class = one whole job (`AuthService` does signup, login, refresh, logout, logoutAll), not one class per step.
- **A constructor takes at most 3 dependencies.** Needing more means the split is wrong.
- Stateless helpers (hashing, signing, cookies, body reading, error mapping) are exported functions in `src/backend/lib/`; classes import and call them directly. Don't wrap them in classes or inject them.
- Plan 01's backend is 7 classes + errors: `Database`, `UserRepository`, `RefreshTokenRepository`, `AuthService(users, refreshTokens, limits)`, `OAuthService(users, authService)`, `AuthController(authService)`, `OAuthController(oauthService)`.
- One class per file, named after the file: `auth.service.ts` → `AuthService`.
- Dependencies come in through the constructor as `private readonly`. Never `new` a dependency inside a method or import a repository/service singleton (only `container.ts` does that).
- Types are plain `interface`s with named fields (`UserRow`, `NewRefreshToken`, `SessionTokens`). No nested `Pick`/`Omit`.

## Layer rules

| Layer | May | Must not |
| --- | --- | --- |
| `route.ts` | export `GET`/`POST`/... and route segment config | hold logic, export helpers |
| Controller | read the request (`readJson`, `readDevice`), set cookies (`setSessionCookies`), map errors (`toErrorResponse`) | hold business rules or run queries |
| Service | business rules, throw `AppError`s | see `Request`/`Response`/cookies |
| Repository | run Drizzle queries, return plain rows or `null` | throw HTTP errors or decide rules |

## Route + controller (App Router only)

```ts
// src/app/api/auth/login/route.ts
import type { NextRequest } from "next/server";
import { authController } from "@/backend/container";
export async function POST(request: NextRequest) { return authController.login(request); }

// Dynamic segment: params is a Promise in Next 16; RouteContext is generated by next dev/build/typegen
export async function GET(request: NextRequest, ctx: RouteContext<"/api/auth/oauth/[provider]/start">) {
  const { provider } = await ctx.params;
  return oauthController.start(request, provider);
}
```

```ts
// src/backend/auth/auth.controller.ts (shape)
constructor(private readonly authService: AuthService) {}         // one dependency

async login(request: NextRequest): Promise<Response> {
  try {
    const body = await readJson(request, loginSchema);              // lib/request.ts; ValidationError on bad body
    const result = await this.authService.login(body, readDevice(request));
    await setSessionCookies(result.tokens);                         // lib/cookies.ts; tokens go only into cookies
    return NextResponse.json({ user: result.user });                // never the tokens
  } catch (error) {
    return toErrorResponse(error);                                  // errors/error-response.ts
  }
}
```

`cookies()` and `headers()` from `next/headers` are async. Read `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` before using another route API.

## Errors

- Throw `NotFoundError`, `UnauthorizedError`, `ValidationError`, `ConflictError` or `TooManyRequestsError` (all extend `AppError`, which carries `message` + `code`).
- `toErrorResponse(error)` is the one place that maps them to `{ error: { message, code } }` plus a status. Anything else becomes 500 "Something went wrong" and gets one `console.error` on the server.
- Another user's row is **404**, never 403. A failed login always says "Email or password is wrong".
- No per-route `try/catch` with hand-written JSON, and no retry loops.

## Drizzle 1.0 RC on Neon

The RC API differs from 0.x tutorials. Check `node_modules/drizzle-orm/*.d.ts` or its README before using a new API.

```ts
// Database: drizzle({ client: pool }) from "drizzle-orm/node-postgres"; pooled Neon URL with ?sslmode=require
export class UserRepository {
  constructor(private readonly database: Database) {}

  async findByEmail(email: string): Promise<UserRow | null> {
    const [row] = await this.database.client
      .select({ id: users.id, fullName: users.fullName, email: users.email,
                passwordHash: users.passwordHash, signInMethod: users.signInMethod })   // explicit columns
      .from(users)
      .where(eq(users.email, email))
      .limit(1);
    return row ?? null;
  }
}
```

- **Select only the columns you need.** Never return `passwordHash` or a token hash beyond the service that needs it.
- **Scope by owner.** User-owned tables filter with `and(eq(t.id, id), eq(t.userId, userId))`; a missing row returns `null`, and the service throws `NotFoundError`.
- **No N+1.** Batch with `inArray(t.id, ids)` and build a `Map`, or use one `innerJoin`/`leftJoin`. Never query inside a `for` loop.
- **Transactions** use `db.transaction(async (tx) => …)` inside one repository method, using `tx` (not `this.database.client`) for every statement. Don't pass `tx` into services.

```ts
// RefreshTokenRepository.rotate: revoke old + insert new atomically
async rotate(oldId: string, next: NewRefreshToken): Promise<boolean> {
  return this.database.transaction(async (tx) => {
    const revoked = await tx.update(refreshTokens)
      .set({ revokedAt: new Date(), replacedBy: next.id })
      .where(and(eq(refreshTokens.id, oldId), isNull(refreshTokens.revokedAt)))  // guard: a racing refresh loses
      .returning({ id: refreshTokens.id });
    if (revoked.length === 0) return false;          // already revoked → service treats it as reuse
    await tx.insert(refreshTokens).values(next);
    return true;
  });
}
```

- **Schema changes:** edit the schema, then `drizzle-kit generate`, then migrate on the Neon `dev` branch (ask first). Never edit generated migrations by hand.

## Upstash Redis (rate limiting only)

Not installed yet: `@upstash/redis` + `@upstash/ratelimit` arrive in Plan 01 step 2. Verify method names and return shapes against the installed `.d.ts` files.

```ts
// lib/rate-limit.ts: a function, not a class
export function createLimiter(name: string, max: number, window: Duration): Limiter
//   builds Ratelimit({ redis, limiter: Ratelimit.slidingWindow(max, window), prefix: `${config.redisKeyPrefix}${name}` })
//   hit(key)   → ratelimit.limit(key)             (counts one attempt; .success false = over)
//   check(key) → ratelimit.getRemaining(key)      (read without counting)
//   reset(key) → ratelimit.resetUsedTokens(key)   (after a good login)

// container.ts: passed into AuthService as one `limits` object, so tests can pass fakes
const authService = new AuthService(userRepository, refreshTokenRepository, {
  login: createLimiter("login", 5, "15 m"), signup: createLimiter("signup", 5, "1 d"),
});
```

- Every key carries `REDIS_KEY_PREFIX` (`dev:` / `prod:`), because dev and prod share one free database.
- Over the limit → the service throws `TooManyRequestsError`. No in-memory counters (they break on Vercel).
- No cache layer is planned. If one is ever needed: `redis.get<T>(key)` and `redis.set(key, value, { ex: seconds })` (Upstash serialises JSON itself, so don't call `JSON.parse`), with the same prefix.

## Auth flow (the pattern every protected route uses)

- `lib/tokens.ts` (jose, HS256): `signAccess`/`verifyAccess` and `signRefresh`/`verifyRefresh`, each with its own secret and a `type` claim so one token can't pass as the other. `sha256()`; only the hash is stored.
- `getCurrentUser()`/`requireUser()` in `auth/current-user.ts` (functions wrapped in React `cache()`): read the access cookie, verify it, load the user, and reject tokens issued before `users.sessions_revoked_at`. Services get the user id from here, never from the request body.
- `AuthService.refresh`: verify the JWT → load the row by `jti` → compare hashes. If revoked or `rotate` returns `false`, `revokeFamily` and throw `UnauthorizedError`.
- `proxy.ts`: optimistic JWT check only, no DB call; the real checks happen in services.
- No roles or RBAC: the only rule is "own rows only".

## Not in this project

No Pages Router (`NextApiHandler`, `req, res`), no Supabase or Prisma, no `ioredis`, no in-memory job queue (there is no queue or worker; anything slow runs inside the request for now), no `jsonwebtoken`, and no Bearer headers (cookies only).
